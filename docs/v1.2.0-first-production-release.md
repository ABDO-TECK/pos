## 3. Migration Architecture & Upgrade Pathways

```
                          ┌───────────────────────────────┐
                          │   Legacy Terminals (<=1.1.46) │
                          └───────────────┬───────────────┘
                                          │ Full Package Ingestion
                                          ▼
                          ┌───────────────────────────────┐
                          │   v1.2.0-bootstrap Migration  │
                          └───────────────┬───────────────┘
                                          │
                  ┌───────────────────────┴───────────────────────┐
                  │                                               │
                  ▼ (Delta Updates)                               ▼ (Delta Updates)
     ┌────────────────────────┐                      ┌────────────────────────┐
     │ Future v1.2.1 Release  │                      │ Future v1.3.0 Release  │
     │ (~50 KB – 500 KB)      │                      │ (Incremental Changes)  │
     └────────────────────────┘                      └────────────────────────┘
```

### Path 1: Legacy Clients (`<= v1.1.46`)
1. Client contacts the update provider (`GitHubReleaseProvider`).
2. Provider detects the client lacks the modern Delta Engine (`update_engine_version` is null).
3. The client receives `v1.2.0-bootstrap` (`full-package.zip`).
4. Staging extracts the complete package with ZipSlip protection, creates a pre-update snapshot, performs atomic file replacement, executes pending database migrations (`045` through `050`), and boots into `v1.2.0`.

### Path 2: Modern Clients (`v1.1.47+`)
1. Client checks for updates.
2. System compares installed version hashes against `manifest.json`.
3. Client downloads lightweight delta zip with only changed binaries and views.
4. Pre-update snapshot is taken, delta files replaced atomically, and status reported to telemetry.

## 4. Rollback & Emergency Recovery Procedures

1. **Automatic Self-Healing Rollback**:
   - If an unexpected power outage, disk write failure, or database error occurs during file replacement, the terminal automatically rolls back on next boot.
   - `UpdateRecoveryService` detects incomplete state, validates the pre-update snapshot in `backend/storage/update-backups/`, restores original files, and resets to `state=idle` in **< 5ms**.
2. **Manual Rollback via Admin Update Center**:
   - Authorized administrators (`updates.rollback` permission) can select any historical snapshot in **Settings > System and Maintenance > Update Center** and click **Rollback**.

---

## 5. How Future Delta Updates Work

Once all terminals are running `v1.2.0`, future updates (e.g. `v1.2.1`, `v1.2.2`, `v1.3.0`) are generated using `generate-delta-package.ps1` or automated GitHub Actions:

1. **Diff Calculation**: CI/CD computes exact git diff between previous tag and current tag.
2. **Small Payloads**: Only changed controllers, services, migrations, and built frontend bundles are packaged into `delta-package.zip` (typically 50 KB – 1.5 MB instead of 45+ MB).
3. **Bandwidth Optimization**: Terminals download updates in seconds, minimizing bandwidth usage on merchant LTE/Wi-Fi connections.
4. **Fleet Telemetry**: Update progress, duration, and success rates report back to the central Fleet Dashboard.
